Desglose Técnico del Código del Laboratorio: azdeploy.py, Dockerfile y main.py

Análisis Exhaustivo de la Lógica de Aprovisionamiento, Empaquetado OCI y Microservicio Flask

1. azdeploy.py — Motor de Automatización y Resiliencia en Azure CLI

El script azdeploy.py implementa un orquestador automatizado en Python que interactúa directamente con la API de Azure CLI mediante subprocess. Sus responsabilidades de diseño clave incluyen:

  • Unicidad Global mediante Hashing Criptográfico SHA-1:
    Calcula un hash de 13 caracteres basado en el nombre del grupo de recursos y la suscripción (hashlib.sha1(...)[:13]) para garantizar nombres de ACR y dominios de Container Apps globalmente únicos sin colisiones DNS.
  • Comprobación Idempotente y Detección de Proveedores:
    Verifica e instala dinámicamente las extensiones containerapp y log-analytics, registrando los namespaces Microsoft.App, Microsoft.OperationalInsights y Microsoft.ContainerRegistry si no están activos.
  • Menú de Despliegue Modular en 5 Fases:
    Opción 1: Compilación serverless con ACR Tasks; Opción 2: Creación del ACA Environment con bucle de reintento; Opción 3: Despliegue de Container App e inyección de secretos; Opción 5: Salida del script.
  • Manejo de Retrasos Transitorios (Transient Delays):
    Monitorea activamente properties.provisioningState == "Succeeded" en el Managed Environment para mitigar el error bloqueante ManagedEnvironmentNotProvisioned en la fase subsiguiente.
  • Generación de Entorno Multiplataforma:
    Exporta los valores resueltos a .env.ps1 (PowerShell) y .env.sh (Bash/macOS), incluyendo CONTAINER_APP_NAME, ACA_ENVIRONMENT, ACR_NAME, RESOURCE_GROUP y TPM_LIMIT.
2. api/Dockerfile — Empaquetado OCI de Producción y Caché de Capas

El contenedor está diseñado siguiendo las directrices de empaquetado OCI seguro y eficiente para microservicios de IA:

  • Imagen Base Minimalista (python:3.12-slim):
    Reduce el tamaño final de la imagen a menos de 150 MB y mitiga vulnerabilidades CVE al prescindir de utilidades innecesarias del sistema operativo Debian.
  • Higiene y Optimización de Capas de Caché:
    Copia primero requirements.txt y ejecuta pip install --no-cache-dir antes de copiar main.py, garantizando que cambios frecuentes en el código de la API no invaliden la compilación de paquetes.
  • Configuración Twelve-Factor y Declaración de Puertos:
    Define ENV PORT=8000 y expone EXPOSE 8000, sirviendo como metadato documental para el balanceador perimetral de Container Apps.
  • Servidor WSGI de Alto Rendimiento (Gunicorn):
    Ejecuta gunicorn --bind 0.0.0.0:${PORT:-8000} --workers 2 --access-logfile - main:app, enviando todos los accesos y errores a stdout para su captura automática por Azure Monitor.
3. api/main.py — Microservicio REST Flask y Diagnóstico de Salud

Microservicio web estructurado para tolerar fallos transitorios e integrarse con sondas de orquestación:

  • Patrón de Fallback Dinámico en Variables de Entorno:
    MODEL_NAME = os.getenv("MODEL_NAME", "not-configured"): Permite que el microservicio inicie incluso si la variable de entorno no se inyectó, permitiendo diagnosticar la anomalía sin colapsar el pod.
  • Sondeo de Salud Desacoplado (GET /health):
    Retorna {"status":"healthy"} con código HTTP 200 de forma inmediata sin depender de servicios externos de red, satisfaciendo los requisitos de Liveness Probe de Container Apps.
  • Descubrimiento de Metadatos del Entorno (GET /):
    Expone un JSON con la versión de la API, el entorno de ejecución (ENVIRONMENT) y el objeto model con su nombre asignado, permitiendo validar la configuración desde el cliente.
  • Trazabilidad Estructurada con UUIDs de Solicitud:
    Las operaciones en POST /process generan un request_id único para correlacionar transacciones distribuidas en Log Analytics sin registrar datos confidenciales (prompts o PII).

Fase 2: Diagnóstico y Resolución de Variables de Entorno Faltantes

Degradación Silenciosa de Microservicios, Inmutabilidad de Revisiones y Restauración de Configuración

Problemática Arquitectónica: Cuando una variable de configuración crítica (Twelve-Factor) se omite o elimina, microservicios resilientes pueden no colapsar gracias a valores por defecto, pero sufren una degradación silenciosa que afecta a los clientes downstream sin generar excepciones fatales inmediatas.
Paso 1 & 2: Eliminación de MODEL_NAME y Creación Automática de Revisión ANOMALÍA INDUCIDA
Elimine la variable MODEL_NAME del contenedor y observe cómo Container Apps crea de inmediato una nueva revisión inmutable:
# 1. Eliminar la variable MODEL_NAME del contenedor az containerapp update ` -n $env:CONTAINER_APP_NAME -g $env:RESOURCE_GROUP ` --remove-env-vars MODEL_NAME # 2. Listar las revisiones para confirmar la creación de una nueva versión inmutable az containerapp revision list ` -n $env:CONTAINER_APP_NAME -g $env:RESOURCE_GROUP -o table
Comportamiento del Modelo de Revisiones: Cada mutación en la sección properties.template (variables, imagen, CPU o réplicas) genera una nueva instantánea inmutable (Revisión). Por defecto, en modo Single Revision, el 100% del tráfico se transfiere inmediatamente a la nueva revisión.
Paso 3: Detección del Síntoma PERSPECTIVA CLIENTE
Consulte la API para constatar la degradación del modelo:
(Invoke-RestMethod -Uri "https://$FQDN/").model # Salida observada: name tpm_limit ---- --------- not-configured 5000
El valor not-configured revela que os.getenv("MODEL_NAME") retornó su fallback.
Paso 4: Inspección de Configuración CAUSA RAÍZ
Inspeccione las variables de entorno inyectadas en el pod:
az containerapp show ` -n $env:CONTAINER_APP_NAME ` -g $env:RESOURCE_GROUP ` --query "properties.template.containers[0].env" ` -o table
La tabla confirma que MODEL_NAME ya no existe en el contenedor.
Paso 5 & 6: Reincorporación de la Variable y Verificación de Restauración RESOLUCIÓN EFECTIVA
Restaure la variable de entorno mediante --set-env-vars y verifique que la API responda nuevamente con gpt-5.1:
# 5. Reinyectar la variable MODEL_NAME (crea una 3ra revisión activa) az containerapp update ` -n $env:CONTAINER_APP_NAME -g $env:RESOURCE_GROUP ` --set-env-vars MODEL_NAME=$env:MODEL_NAME # 6. Validar que la API retorne el nombre de modelo correcto (Invoke-RestMethod -Uri "https://$FQDN/").model # Salida esperada tras la corrección: name tpm_limit ---- --------- gpt-5.1 5000
Navegación Visual en Azure Portal: Diríjase a Container Apps > ai-api > Configuración > Variables de aplicación. Observe cómo la variable MODEL_NAME se encuentra presente y, en la sección Administración de revisiones, compruebe que la última revisión creada gestiona ahora el 100% del tráfico de red.

Fase 3: Diagnóstico y Corrección de Port Mismatch e Ingress 503

Enrutamiento Envoy Ingress, Desajuste de Target Port, Análisis de Logs y Restauración

Problemática Arquitectónica: Azure Container Apps utiliza Envoy como proxy inverso perimetral. Si el parámetro target-port configurado en el Ingress difiere del puerto TCP en el que el servidor WSGI (Gunicorn) está vinculado (0.0.0.0:8000), Envoy no puede establecer conexión TCP con el pod, generando un error global HTTP 503 Service Unavailable (Connection Refused) en todas las rutas.
Paso 1 & 2: Inducción de Desajuste de Puerto (Target Port 3000) y Error 503 PORT MISMATCH
Modifique el puerto de destino del Ingress a 3000 e intente consumir el endpoint de sondeo de salud:
# 1. Configurar el puerto de entrada a 3000 (desajuste con Gunicorn en 8000) az containerapp ingress update ` -n $env:CONTAINER_APP_NAME -g $env:RESOURCE_GROUP ` --target-port 3000 # 2. Intentar consultar el endpoint de salud desde el cliente HTTP Invoke-RestMethod -Uri "https://$FQDN/health" # Error HTTP arrojado en el cliente: # Invoke-RestMethod: The remote server returned an error: (503) Server Unavailable. # Detalle interno Envoy: "upstream connect error or disconnect/reset before headers. reset reason: connection failure"
Paso 3a: Inspección de Ingress PLANO DE ENTRADA
Verifique la configuración activa en el proxy perimetral Envoy:
az containerapp show ` -n $env:CONTAINER_APP_NAME ` -g $env:RESOURCE_GROUP ` --query "properties.configuration.ingress" ` -o yaml # Evidencia: fqdn: ai-api.wonderfulplant-... targetPort: 3000
Paso 3b: Logs del Contenedor PLANO DE CÓMPUTO
Compruebe si la app está viva y en qué puerto escucha:
az containerapp logs show ` -n $env:CONTAINER_APP_NAME ` -g $env:RESOURCE_GROUP # Evidencia en salida Gunicorn: [INFO] Starting gunicorn 22.0.0 [INFO] Listening at: http://0.0.0.0:8000
Paso 4 & 5: Corrección de Target Port a 8000 y Verificación de Salud RESOLUCIÓN EFECTIVA
Alinee el puerto de destino del Ingress con el puerto 8000 y confirme la recuperación de la API:
# 4. Restablecer el target-port correcto a 8000 az containerapp ingress update ` -n $env:CONTAINER_APP_NAME -g $env:RESOURCE_GROUP ` --target-port 8000 # 5. Verificar la accesibilidad del endpoint de sondeo de salud Invoke-RestMethod -Uri "https://$FQDN/health" # Salida esperada tras la alineación de puertos: {"status": "healthy"}
Navegación Visual en Azure Portal: En la hoja Container Apps > ai-api > Entrada, localice el campo Puerto de destino. Modifique el valor de 3000 a 8000 y presione Guardar. Observe en Transmisión de registros cómo las peticiones HTTP retornan inmediatamente con código 200 OK.

Fase 4: Observabilidad Histórica con Log Analytics y Consultas KQL

Supervisión de Registros de Consola y Sistema, Extracción de Workspace ID y Telemetría Forense

Diferenciación Arquitectónica de Logs: Los registros de consola mostrados por az containerapp logs show son recientes y volátiles (se pierden tras reinicios o recreaciones de réplicas). Para investigación forense, cumplimiento y análisis histórico, los logs persisten en el área de trabajo de Azure Log Analytics vinculada al Environment.
Paso 1: Extracción del Customer ID del Log Analytics Workspace ID RESOLUTION
Obtenga el identificador único del área de trabajo asociada al Container Apps Environment para dirigir las consultas KQL:
# Extraer el Customer ID de Log Analytics desde las propiedades del entorno $WORKSPACE_ID = az containerapp env show ` -n $env:ACA_ENVIRONMENT -g $env:RESOURCE_GROUP ` --query properties.appLogsConfiguration.logAnalyticsConfiguration.customerId ` -o tsv Write-Output "Workspace ID: $WORKSPACE_ID"
Paso 2: Últimos 20 Logs de Consola KQL CONSOLA
Consulta sobre la tabla ContainerAppConsoleLogs_CL:
az monitor log-analytics query ` -w $WORKSPACE_ID ` --analytics-query "ContainerAppConsoleLogs_CL | where ContainerAppName_s == '$env:CONTAINER_APP_NAME' | project TimeGenerated, Log_s | order by TimeGenerated desc | take 20" -o table
Paso 3: Filtrado de Logs de Error KQL ERRORES
Aislamiento de excepciones y fallos en runtime:
az monitor log-analytics query ` -w $WORKSPACE_ID ` --analytics-query "ContainerAppConsoleLogs_CL | where ContainerAppName_s == '$env:CONTAINER_APP_NAME' and Log_s contains 'error' | project TimeGenerated, Log_s | order by TimeGenerated desc | take 20" -o table
Paso 4: Supervisión de Eventos de Plataforma (ContainerAppSystemLogs_CL) SYSTEM LOGS
A diferencia de los logs de aplicación, la tabla ContainerAppSystemLogs_CL captura eventos de la infraestructura subyacente (fallos de pull de imagen en ACR, escala a cero, fallos de sondeos y reinicios de réplica):
# Consultar eventos del orquestador (extracciones OCI, reinicios OOM, sondas fallidas) az monitor log-analytics query ` -w $WORKSPACE_ID ` --analytics-query "ContainerAppSystemLogs_CL | where ContainerAppName_s == '$env:CONTAINER_APP_NAME' | project TimeGenerated, EventType_s, Reason_s, Log_s | order by TimeGenerated desc | take 10" -o table
Consideraciones Operativas y Directrices de Observabilidad en IA
  • Latencia de Ingesta (2 a 5 minutos): Los datos de Log Analytics experimentan un retraso transitorio tras su emisión; use az containerapp logs show para monitoreo en vivo inmediato y Log Analytics para auditoría.
  • Trazabilidad Estructurada sin Filtración de Secretos: Incluya siempre request_id, versión del modelo (gpt-5.1) y latencias de inferencia; NUNCA registre contenido confidencial de prompts o documentos para cumplir con GDPR y normativas de privacidad.

Ciclo de Vida, Sondeos de Salud, Identidad de Imagen y Optimización de Cómputo

Directrices Oficiales de Microsoft Learn para Operaciones del Día Dos en Contenedores de IA

1. Identidad de Imagen: Tags vs. Digest SHA-256

Slide 18 Oficial: En entornos de producción y misiones críticas, la trazabilidad del binario es prioritaria:

  • Etiquetas Mutables (:latest): Son convenientes para desarrollo, pero representan un riesgo operacional al cambiar de contenido sin previo aviso.
  • Resúmenes Inmutables (@sha256:...): Garantizan que todas las réplicas ejecuten exactamente el mismo artefacto binario, facilitando la correlación forense durante incidentes.
  • Estrategia de Retención de Revisiones: Conserve revisiones inactivas con errores para análisis forense antes de depurarlas.
2. Operaciones de Ciclo de Vida y Mitigación

Slide 19 Oficial: Elección de la acción adecuada según la severidad del incidente:

  • Desactivar Revisión (Recomendado): Aísla la versión defectuosa de forma inmediata. Es el primer paso más seguro ante fallos de despliegue.
  • Reiniciar (Restart): Borra estado transitorio y soluciona bloqueos de subprocesos o fugas de memoria temporales.
  • Detener (Stop): Garantiza cero tráfico y cero consumo de cómputo. Uso reservado para incidentes mayores.
3. Sondeos de Salud (Probes) en Modelos de IA

Slide 21 Oficial: Calentamiento de pesos y prevención de deadlocks:

  • Readiness Probe (Preparación): Protege el contenedor durante la carga del modelo en memoria; configure initialDelaySeconds y un failureThreshold generoso para evitar descartes prematuros.
  • Liveness Probe (Vivacidad): Detecta deadlocks y reinicia el pod. NUNCA debe depender de servicios externos (ej. Cosmos DB o APIs externas) para evitar reinicios en cascada.
4. Dimensionamiento y Reglas de Escalado

Slide 22 Oficial: Equilibrio entre coste, rendimiento y latencia:

  • CPU Throttling: Si los logs reportan limitación de CPU, aumente primero la asignación de vCPU por réplica antes de modificar las reglas de autoescalado.
  • Reinicios OOM (Out Of Memory): Indican que la réplica superó su cuota RAM; incremente la memoria asignada.
  • Estrategias: APIs síncronas requieren minReplicas >= 1 para eliminar arranques en frío; workers en background escalan a cero.

Caso 1 (Slide 24 Oficial): Trazabilidad de Imagen en Despliegues de Producción DOMINIO 1
Escenario: Implementará una nueva imagen en una aplicación contenedora de producción. ¿Qué enfoque proporciona la mejor rastreabilidad y reduce el riesgo de implementar el artefacto incorrecto?
A) Hacer referencia a la imagen por la etiqueta latest.
B) [CORRECTA] Hacer referencia a la imagen por su resumen (Digest SHA-256).
C) Recompilar la imagen localmente en cada entorno de despliegue.
Justificación Oficial Exhaustiva: Las etiquetas (tags) son punteros mutables que pueden sobrescribirse involuntariamente. El resumen (Digest criptográfico SHA-256) es estrictamente inmutable; garantiza que todas las réplicas ejecuten idéntico artefacto y permite correlacionar inequívocamente el comportamiento del sistema con una compilación auditada. La opción C introduce divergencia entre entornos (environment drift).
Caso 2 (Slide 24 Oficial): Latencia y Limitación de CPU en Cargas de IA OPTIMIZACIÓN
Escenario: Su API de IA muestra alta latencia y los mensajes de registro indican limitación de CPU (CPU throttling) durante picos de tráfico. ¿Qué cambio se dirige más directamente a resolver la limitación?
A) [CORRECTA] Aumentar la asignación de CPU por réplica y, a continuación, volver a evaluar las reglas de escalado.
B) Desactivar la revisión más reciente para reducir la carga de cómputo.
C) Cambiar la referencia de la imagen de resumen (digest) a etiqueta (tag).
Justificación Oficial Exhaustiva: Cuando los subprocesos de inferencia de un contenedor saturan su cuota de CPU asignada por cgroups, añadir más réplicas no soluciona el problema si cada réplica individual sufre estrangulamiento. Primero debe redimensionarse la CPU por réplica para satisfacer la demanda de procesamiento y posteriormente calibrar las métricas de autoescalado. La opción B provoca indisponibilidad y la C es irrelevante.
Caso 3: Ingress 503 Mismatch
Tras actualizar target-port a 3000, los clientes reciben HTTP 503. ¿Cuál es la causa raíz?
Solución: Desajuste entre el proxy Envoy y el socket TCP de Gunicorn (8000). Envoy no puede reenviar tráfico a un puerto cerrado.
Fix: az containerapp ingress update --target-port 8000.
Caso 4: Fallback Env Var
Al eliminar MODEL_NAME, la API responde con not-configured sin colapsar. ¿Por qué?
Solución: El microservicio implementa fallback con os.getenv("MODEL_NAME", "not-configured"), mitigando un crash fatal.
Principio: Container Apps crea una nueva revisión inmutable para cada cambio.
Caso 5: Diagnóstico Forense KQL
Una réplica sufrió un reinicio OOMKilled hace 3 horas. az containerapp logs show no muestra registros. ¿Cómo auditarlo?
Solución: Consultar ContainerAppConsoleLogs_CL y ContainerAppSystemLogs_CL en Log Analytics Workspace con KQL.
Rationale: Los logs de consola son volátiles; Log Analytics persiste hasta 730 días.

Glosario de Términos, Conceptos Clave y Siglas de Azure

Definiciones Normativas de Azure Container Apps, Diccionario de Siglas y Mapa Curricular Oficial

1. Conceptos Arquitectónicos Centrales de Azure Container Apps
Revisión Inmutable (ACA)
Instantánea versionada que congela la imagen OCI, variables de entorno, cuotas de vCPU/RAM y secretos. Cualquier actualización crea una nueva revisión sin mutar contenedores en caliente.
Target Port & Envoy Ingress
Puerto TCP del contenedor hacia el cual el proxy Envoy reenvía tráfico tras terminar TLS 1.3 en el FQDN. Un desajuste con el socket de Gunicorn (ej. 3000 vs 8000) genera un error 503.
Image Digest SHA-256
Hash criptográfico inmutable que identifica unívocamente el binario de la imagen en ACR, eliminando la ambigüedad y riesgos operacionales de las etiquetas mutables (:latest).
Readiness Probe en IA
Sonda de preparación que retiene el tráfico HTTP hasta que el microservicio finaliza la carga de pesos del modelo de IA en memoria, evitando respuestas erróneas a clientes iniciales.
Liveness Probe & Deadlocks
Sonda de vivacidad periódica que comprueba la salud interna del proceso y gatilla su reinicio ante interbloqueos; nunca debe depender de bases de datos o servicios externos.
Log Analytics & KQL
Repositorio centralizado persistente que almacena ContainerAppConsoleLogs_CL y eventos de sistema ContainerAppSystemLogs_CL para diagnóstico forense post-reinicio.
