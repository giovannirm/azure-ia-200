Prerrequisitos Universales del Entorno

• Suscripción de Azure: Requiere plan con soporte de App Service Linux dedicado (ej. B1 o P0v3).

• Azure CLI: Versión 2.50+ instalada localmente o en Azure Cloud Shell (az --version).

• Python 3.10+: Para ejecutar scripts de despliegue automatizado de infraestructura (azdeploy.py).

• Permisos RBAC: Roles Contributor y User Access Administrator u Owner para asignación de roles.

• Sin Docker local: No se requiere Docker Desktop; la imagen se compila en ACR Tasks y se corre en PaaS.

Avisos Críticos y Consideraciones de Azure

• DNS Global Único: Los nombres de ACR (*.azurecr.io) y Web Apps (*.azurewebsites.net) son públicos y únicos.

• Propagación de Roles: Las asignaciones de roles RBAC en Entra ID tardan típicamente entre 60 y 120 segundos.

• Sintaxis de Consola: Se documenta sintaxis dual: PowerShell (acento grave `) y Bash (barra invertida \).

• Almacenamiento Efímero: Por defecto, los contenedores Linux en App Service no persisten archivos sin configurar /home.

Fundamento de Azure App Service: Dualidad Web App (Carga Lógica) vs App Service Plan (Cómputo Físico)

• Modelo PaaS Totalmente Administrado: Abstracción completa de infraestructura. Azure gestiona el aprovisionamiento de VMs, parches del kernel de Linux, balanceo de carga L7 y terminación TLS/SSL sin sobrecarga operativa.

• Web App (Carga Lógica y Runtime): Entorno donde reside la aplicación (código o contenedor OCI). Encapsula configuraciones (App Settings), variables de entorno, certificados SSL, dominios personalizados y ranuras de despliegue (deployment slots).

• App Service Plan (Cómputo Físico y Costos): Representa la granja dedicada de servidores virtuales subyacente. Define la región geográfica, cantidad de núcleos vCPU, memoria RAM disponible, límites de escalado elástico y el nivel de facturación (SKU).

• Densidad y Aislamiento Multitenant: Múltiples Web Apps pueden cohabitar en un mismo App Service Plan compartiendo recursos para optimizar costos, o aislarse en planes dedicados para garantizar rendimiento predecible en producción.

1. azdeploy.py (Automatización de Infraestructura) Infraestructura como Código

Script en Python que orquesta el aprovisionamiento de recursos en Azure sin requerir plantillas Bicep ni Terraform:

  • Variables de entrada (L8-54): Define rg (Resource Group), location (región, ej. canadacentral o eastus) y sku (cómputo, por defecto P0v3 o alternativo B1). Son los parámetros configurables de usuario.
  • Ajuste de SKU de Cómputo: Incluye especificaciones arquitectónicas de tiers (Basic, Standard, Premium v3 e Isolated v2). Por defecto utiliza sku = "P0v3" (Premium v3 de entrada, 1 vCPU / 4 GB RAM) o sku = "B1" (Basic para suscripciones con cuota ajustada).
  • Identidad y Hashing único (L121-128): Obtiene el Object ID de Entra ID mediante az ad signed-in-user show, calcula un hash SHA-1 de 8 caracteres y deriva los nombres acr{user_hash}, plan-docprocessor-{user_hash} y app-docprocessor-{user_hash}, garantizando unicidad global de FQDN.
  • Idempotencia en Recursos (L147-233): Comprueba la existencia previa de Resource Group, ACR y App Service Plan antes de crearlos.
  • Exportación Multi-Shell (L88-120): Escribe .env (para Bash: export VAR="...") y .env.ps1 (para PowerShell: $env:VAR = "...") con saltos LF para interoperabilidad universal.
2. api/Dockerfile (Definición de Contenedor OCI) Contenedor OCI

Especificación de capas optimizada para ejecución de microservicios en Azure App Service sobre Linux:

  • FROM python:3.11-slim: Imagen oficial reducida basada en Debian (~150 MB), minimizando la superficie de ataque y el tiempo de extracción de capas.
  • COPY requirements.txt . && RUN pip install --no-cache-dir -r requirements.txt: Cacheo de dependencias de Flask y Gunicorn sin almacenar tarballs temporales de pip.
  • RUN mkdir -p /home/processed: Prepara el directorio de almacenamiento local (en App Service se montará sobre volumen CIFS compartido).
  • EXPOSE 80: Declara el puerto de escucha que el proxy reverso frontal de App Service detecta automáticamente.
  • CMD ["gunicorn", "--bind", "0.0.0.0:80", "--workers", "2", "--access-logfile", "-", "main:app"]: Arranca el servidor WSGI en formato exec (JSON array) para propagación directa de señales SIGTERM y logging a stdout.
3. api/main.py (Microservicio Flask de Procesamiento de Documentos) Microservicio REST

Servidor REST que simula inferencia de IA (extracción de entidades, palabras clave, análisis de sentimiento) y persistencia:

  • Configuración Twelve-Factor (L13-21): Ingesta variables operativas mediante os.getenv() (MAX_DOCUMENT_SIZE_MB, STORAGE_PATH, ENVIRONMENT).
  • Ruta /health: Health check probe ligero para los sondeos de disponibilidad (Liveness Probe) del balanceador PaaS de App Service.
  • Ruta /process: Ingiere texto o JSON, valida límites de tamaño (413), calcula métricas y persiste el resultado en STORAGE_PATH/{doc_id}.json.
  • Ruta /documents: Inspecciona el volumen montado y expone la lista de documentos analizados para auditoría.
4. api/requirements.txt (Dependencias del Microservicio de IA) Librerías Python

Lista estricta de dependencias sin fijación de build-tools para evitar almacenamiento redundante en capas OCI:

  • Flask==3.0.0: Framework WSGI ligero para la API REST de procesamiento y controladores de endpoints.
  • gunicorn==21.2.0: Servidor HTTP WSGI para UNIX de producción con soporte de múltiples workers concurrentes.
  • werkzeug==3.0.1: Utilidades WSGI subyacentes para parseo seguro de solicitudes, cabeceras y manejo de payloads.

Mapeo de Puertos y Enrutamiento Interno

• Detección automática: App Service analiza el contenedor y detecta la cláusula EXPOSE 80 del Dockerfile.

• Proxy inverso frontal: El balanceador PaaS recibe solicitudes públicas en los puertos 80/443 (HTTPS) y las redirige internamente al puerto en el que escucha Gunicorn (puerto 80).

• Variable WEBSITES_PORT: Si la aplicación escucha en un puerto personalizado (ej. 5000 o 8080), es obligatorio definir WEBSITES_PORT=80 en Application Settings.

• Enlace a 0.0.0.0: En contenedores Docker, la aplicación debe enlazar a 0.0.0.0 (no a 127.0.0.1), de lo contrario el proxy de App Service no podrá alcanzar el servicio.

Timeout de Inicio del Contenedor

• Límite predeterminado: App Service espera hasta 230 segundos a que el contenedor responda a las sondas HTTP iniciales antes de abortar el arranque.

• Modelos pesados de IA: Si la aplicación descarga pesos de modelos o bibliotecas pesadas durante el arranque, este tiempo puede ser insuficiente.

• Variable de ampliación: Se debe configurar WEBSITES_CONTAINER_START_TIME_LIMIT=600 (configurable hasta un máximo de 1800 segundos / 30 minutos).

• Diagnóstico de fallos: Si el contenedor se reinicia en bucle (crash loop), revise los logs del motor Docker en Kudu.

Diagrama de Arquitectura Física y Red de App Service

Topología de red perimetral, plano de datos aislado, servicio IMDS y montaje CIFS/SMB cifrado

Topología de Red y Fronteras de Aislamiento Físico

Aislamiento de Cómputo: El App Service Plan Linux aprovisiona instancias de máquinas virtuales dedicadas protegidas por Azure Hyper-V y cgroups. El tráfico de producción ingress en el puerto 443 es terminado en el balanceador frontal PaaS de Azure y reenviado por un canal local al contenedor Docker en 0.0.0.0:80.

Autenticación Criptográfica IMDS: La identidad administrada consulta internamente al Azure Instance Metadata Service (http://169.254.169.254/metadata/identity/oauth2/token), una dirección local no enrutable a Internet. Los tokens obtenidos son enviados por TLS 1.3 hacia el plano de datos de Azure Container Registry.

TOPOLOGÍA DE RED Y PLANO FÍSICO (DRAW.IO CANVAS ESTILO VECTORIAL) TLS 1.3 • IMDS 169.254.169.254 • SMB Port 445
Aspectos Clave de Seguridad de Red: (1) Terminación TLS: El balanceador PaaS frontal de Azure gestiona certificados SSL y mitiga ataques de capa 7 antes de alcanzar el nodo Linux. (2) Cero Tráfico de Credenciales: El daemon IMDS entrega tokens en memoria sin exponer secretos en el canal de red público. (3) Montaje de Red Cifrado: El almacenamiento en /home se comunica por canal CIFS interno cifrado con AES-256 gestionado por Microsoft.

Regla 1: Autenticación Zero-Trust

Regla 2: Persistencia CIFS en /home

Una imagen de contenedor escucha en el puerto 8000. Después de la implementación en App Service, las solicitudes devuelven errores de conexión. ¿Qué resuelve este problema?
A) Modificar el Dockerfile para usar EXPOSE 80.

✓ Respuesta Correcta: B) Establecer la configuración de la aplicación WEBSITES_PORT en 8000

• Por qué WEBSITES_PORT=8000:

- Instruye al proxy inverso PaaS hacia qué puerto privado interno debe reenviar el tráfico entrante.

• Por qué falla EXPOSE 80 (Distractor A):

- EXPOSE en Docker es solo metadato documental; no cambia el socket TCP que el proceso de la app abre en runtime (sigue en 8000).

• Regla de Oro de Arquitectura:

- Cualquier puerto distinto de 80/8080 exige WEBSITES_PORT. En producción, incluso con puerto 80, configurarlo explícitamente suprime la latencia de autodetección de Azure.

Unidad de cómputo físico/virtual que determina la región, el número de instancias, el SO (Linux/Windows), vCPUs y memoria RAM asignados a una o varias Web Apps.
Web App for Containers
Servicio PaaS administrado que ejecuta contenedores Docker/OCI en Linux con balanceo de carga integrado, certificados SSL gratuitos y escalado automático.
System-Assigned Identity
Identidad administrada ligada al ciclo de vida del recurso en Microsoft Entra ID. Proporciona autenticación sin contraseñas para interactuar con ACR y Key Vault.
Almacenamiento Persistente /home
Volumen de red compartido (SMB/CIFS) respaldado por Azure Storage montado en /home cuando WEBSITES_ENABLE_APP_SERVICE_STORAGE=true.
Kudu / SCM Engine
Plano de control y motor de gestión de App Service accesible en <app>.scm.azurewebsites.net, encargado de pulls de imagen, WebSSH y telemetría de log.
Container Logging Stream
Mecanismo de captura y retransmisión en tiempo real de los flujos stdout y stderr del contenedor Docker hacia Azure CLI y Azure Monitor.
Deployment Slot (Ranura)
Entorno de hospedaje secundario aislado con FQDN propio para pruebas previas al pase a producción, con soporte de variables pegadas (slot settings) que no se intercambian.
Key Vault Reference
Directiva declarativa @Microsoft.KeyVault(...) que resuelve secretos en memoria al iniciar el contenedor mediante Managed Identity sin librerías en el código.
Startup Command Override
Instrucción en App Service que reemplaza la directiva CMD del Dockerfile (manteniendo ENTRYPOINT) para ejecutar migraciones o argumentos dinámicos.
2. Diccionario de Siglas y Acrónimos Técnicos del Módulo
Sigla Significado y Rol en Azure
AAS Azure App Service: Plataforma PaaS administrada para hospedar aplicaciones web y contenedores.
ASP App Service Plan: Asignación de recursos de proceso (CPU, memoria, SKU y escala) para Web Apps.
ACR Azure Container Registry: Registro privado administrado para almacenamiento y compilación OCI.
RBAC Role-Based Access Control: Control de acceso basado en roles (AcrPull, Contributor).
MI / MSI Managed Identity / Managed Service Identity: Identidades sin contraseña gestionadas por Entra ID.
OCI Open Container Initiative: Estándar de la industria para formatos de imagen y runtimes de contenedores.
KUDU Kudu Engine: Motor de despliegue, administración y diagnóstico asociado a cada Web App.
SCM Site Control Manager: Endpoint administrativo aislado en <app>.scm.azurewebsites.net.
FQDN Fully Qualified Domain Name: Nombre de dominio completo (ej. <app>.azurewebsites.net).
CMD Command: Directiva de inicio en Dockerfile sobreescribible con el parámetro startup-file.
KQL Kusto Query Language: Lenguaje de consulta analítica para telemetría en Log Analytics.
Sigla Significado y Rol en Azure
TLS Transport Layer Security: Protocolo criptográfico (TLS 1.3) que cifra el canal HTTPS de la Web App.
CIFS / SMB Common Internet File System: Protocolo de red usado para montar /home desde Azure Storage.
IMDS Instance Metadata Service: Endpoint local 169.254.169.254 para emisión de tokens Entra ID.
SKU Stock Keeping Unit: Nivel de tarificación y capacidad de cómputo (Basic B1, Premium P0v3).
WSGI Web Server Gateway Interface: Interfaz estándar entre servidores web (Gunicorn) y Python Flask.
REST Representational State Transfer: Arquitectura de servicios web sin estado sobre protocolo HTTP.
CORS Cross-Origin Resource Sharing: Mecanismo de seguridad para autorizar peticiones entre dominios.
ARM Azure Resource Manager: Plano de control declarativo para gestionar infraestructura en Azure.
CVE Common Vulnerabilities and Exposures: Identificador público estandarizado de fallos de seguridad.
DNS Domain Name System: Servicio de resolución de nombres con ámbito global único (FQDN).
MIME Multipurpose Internet Mail Extensions: Formato estándar de tipos de contenido HTTP (API REST).
